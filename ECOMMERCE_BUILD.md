# E-commerce build tracker

Two-sided store: admin manages a nested category tree, brands, products with
variants (e.g. Size/Color), and media; customers browse and buy, checking out
through SumUp. Built in 7 phases so the app stays working and testable after
each one — **build and verify in order, don't skip ahead**.

Full detailed plan (schema, exact file paths, package list) lives at
`C:\Users\Ian\.claude\plans\breezy-beaming-meadow.md`. This file is the
quick-reference status tracker.

## Locked-in decisions

- Admin access: plain `role` column on `users` (no spatie/permission).
- Products have real variants (options + values + variant SKUs), not simple flat products.
- Categories: `kalnoy/nestedset` (arbitrary depth).
- Media: `spatie/laravel-medialibrary`.
- Cart: session-based, no DB cart table.
- Payment: **SumUp only** for now, via their REST API (no official SDK) — OAuth2
  client-credentials + Checkout API + webhook that re-verifies status server-side.
- No JS build tooling — pure Blade + Bootstrap 5 (CDN) + jQuery (CDN), no
  Vite/Alpine/Livewire. Admin UI built the same way, full page reloads.

- [x] **Phase 7 — SumUp integration** *(done)*
  - `.env`/`.env.example`: `SUMUP_API_KEY`/`SUMUP_MERCHANT_CODE`. `config/services.php` → `sumup` block reading them.
    - **Correction after real-account testing**: the plan's original design (`SUMUP_CLIENT_ID`/`SECRET`, OAuth2 client-credentials) assumed a multi-merchant OAuth app. A single-merchant integration like this one instead just gets a secret API key (`sup_sk_...`) used directly as a bearer token — no token exchange step, and no separate sandbox host. Confirmed directly against SumUp's API: the OAuth `/token` call returned `invalid_client`, while the same key as a plain bearer token against `/v0.1/me` and `/v0.1/checkouts` worked immediately. `SumUpClient` was simplified accordingly (no `getAccessToken()`/token caching — the configured key is used as-is).
    - Also caught and fixed a related bug this surfaced: `CheckoutController::store` builds the SumUp payload from `$order->currency` immediately after `Order::create()`, but `currency` was never passed explicitly — only defaulted at the DB level, which Eloquent doesn't know about until a refresh, so it read as `null` in-memory and SumUp rejected the request. Now set explicitly (`'currency' => 'GBP'`) at create time; regression-tested by asserting the actual outgoing request body.
  - `app/Services/SumUp/SumUpClient.php` — `createCheckout(array $payload)`, `getCheckout(string $checkoutId)`.
    - **Second correction**: SumUp's Checkout API has no generic hosted redirect page at all (there's no Stripe-Checkout-style `checkout.sumup.com/pay/{id}` — that was another guess that turned into a live 404, caught by the user actually clicking through). The real integration is SumUp's own embeddable **Card Widget**: `GET /checkout/{order}/pay` (`CheckoutController::pay`) now renders `shop/checkout/pay.blade.php`, which loads `https://gateway.sumup.com/gateway/ecom/card/v2/sdk.js` and calls `SumUpCard.mount({ id, checkoutId, onResponse })` — confirmed against SumUp's actual developer docs (fetched directly, not recalled from memory, after the first two guesses both failed) rather than guessed a third time. `onResponse`'s `success` type only means the widget's own request completed, not that the payment succeeded (SumUp's docs say so explicitly) — the page still just forwards to `checkout.return`, a holding page; the webhook (re-verified server-to-server against SumUp) remains the only thing that actually marks an order paid.
  - `CheckoutController::store` now wraps order+item creation *and* the `createCheckout()` call in one `DB::transaction` — if SumUp can't be reached or rejects the request, the whole thing rolls back (no orphaned pending order) and the shopper is bounced back to checkout with an error, cart untouched so they can just retry. On success the browser is redirected to `checkout.pay`.
  - `GET /checkout/{order}/return` and `POST /checkout/{order}/return` (`CheckoutController::returnFromSumUp`, one route, `Route::match(['get','post'], ...)`):
    - **Third correction, this one caught by the user reporting real transactions staying "pending"**: SumUp's Checkout API has **no separately configured webhook URL at all** — confirmed directly from SumUp's own webhook docs (fetched, not recalled). It POSTs the `CHECKOUT_STATUS_CHANGED` notification straight to the checkout's own `return_url`, i.e. this exact route. The standalone `POST /api/webhooks/sumup` built earlier was never being called by SumUp for this integration — dead code that made orders look like they were stuck "pending" even for genuinely failed/succeeded payments, since nothing ever told the app what happened. Fixed by making `returnFromSumUp` branch on request method: POST re-verifies the checkout against SumUp (`SumUpCheckoutStatusSync::sync()`) and returns an empty `200`, with no `isViewableInThisSession()` gate (a server-to-server POST carries no session to check); GET still shows the "confirming your payment" holding page to the shopper's own browser, gated as before. Added a CSRF exception for `checkout/*/return` in `bootstrap/app.php` (`validateCsrfTokens(except:)`), since SumUp's POST carries no Laravel CSRF token.
    - The shared verification logic (re-fetch from SumUp, mark paid + decrement stock idempotently, mark failed, send `OrderPaid`) was extracted into `app/Services/SumUp/SumUpCheckoutStatusSync.php` so both this route and the now-secondary `SumUpWebhookController` use the same code instead of duplicating it.
    - Either way, this still deliberately does **not** trust a bare "the widget said success" — the widget's `onResponse` callback only forwards the shopper to this URL's GET; only the POST (re-verified against SumUp directly) actually changes the order's status.
  - `app/Http/Controllers/SumUpWebhookController.php` at `POST /api/webhooks/sumup` (`routes/api.php`) — kept only as a defensive fallback in case a future SumUp account type does support a separately configured webhook URL; not what's actually called for this integration (see above).
  - `app/Notifications/OrderPaid.php` (queued, mail channel) — sent via `Notification::route('mail', $order->contact_email)->notify(...)` rather than `$order->user->notify()`, since a guest order has no account to notify through. `MAIL_MAILER=log` in dev, as already noted — real SMTP creds needed before this actually delivers anywhere.
  - Test: `tests/Feature/Shop/CheckoutReturnWebhookTest.php` — the real mechanism: POST to `checkout.return` with no session marks paid + decrements stock (idempotent against a repeat), a forged `status` field in the body is ignored, marks failed, and isn't gated by session ownership the way GET still is. `tests/Feature/Shop/SumUpWebhookTest.php` covers the same behaviour for the secondary fallback route. Extended `tests/Feature/Shop/CheckoutTest.php` with `Http::fake()` for the checkout-creation endpoint (existing tests needed it once `store()` started making a real call), a test for a failed SumUp call rolling back the order/leaving the cart intact, a currency-payload regression test, and pay-page rendering/authorization tests. All 134 tests pass.
  - Verified against the **real** SumUp account throughout, correcting course each time reality disagreed with a guess: (1) OAuth client-credentials → `invalid_client`, switched to the account's actual auth model (secret API key as a bearer token, confirmed via `/v0.1/me`); (2) a guessed hosted-redirect URL → live 404 the user caught by clicking through, switched to SumUp's real Card Widget after fetching their actual docs; (3) the user reporting real sandbox transactions staying "pending" despite SumUp itself reporting them `FAILED` → traced to the dead `/api/webhooks/sumup` route and fixed as above, confirmed by POSTing a simulated status-changed notification straight at `/checkout/{order}/return` on a local order and getting a `200` with no CSRF rejection. Also caught, mid-fix, that `.env`'s `SUMUP_MERCHANT_CODE` legitimately holds the account's **sandbox** merchant code (`merchant_sandbox: true` in SumUp's own response) distinct from its live one — don't "fix" that value again without checking `merchant_sandbox` first. Sandbox mode only recognizes SumUp's own designated test cards (success: `4200 0000 0000 0091`; 3DS challenge: `4200 0000 0000 0042`; any card fails outright at checkout amounts of exactly `11.00`/`42.01`/`42.76`/`42.91`) — a real card number will always decline there, which is separate from (and not fixed by) the webhook wiring fix. Test orders created during all of this were deleted afterward; no real payment was ever submitted.
  - Also found and fixed a real secrets-hygiene issue while wiring this up: `.env.example` (a committable template) had picked up the real secret key and merchant identifiers, seemingly copied over from `.env` while it was open. Confirmed via `git status`/`git diff` that this was still an uncommitted working-tree change — never pushed, no rotation needed — and reset `.env.example` back to blank placeholders. `.env` itself is correctly gitignored throughout.
